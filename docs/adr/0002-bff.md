# 0002: A backend-for-frontend instead of calling the upstream API directly

## Context

The frontend needs data from the Laravel API at `nesthus.no`, plus
third-party marine/aircraft data (BarentsWatch AIS, ADS-B). Calling all of
these directly from the browser was considered and rejected.

## Decision

Introduce a small Node/TypeScript BFF (Fastify) that the frontend talks to
exclusively. The BFF proxies and shapes upstream responses, applies caching,
and holds any third-party credentials.

## Consequences

- **No CORS configured upstream.** `nesthus.no` does not serve CORS headers
  for browser-origin requests from a separate app; a BFF avoids needing to
  change that on the upstream side.
- **Shared rate limits are not kiosk-safe.** The upstream API's per-IP rate
  limiter is sized for normal browsing, not a kiosk polling every few
  seconds; a BFF can cache and coalesce requests so the kiosk doesn't starve
  the limiter (or itself, if other clients share the same public IP).
- **Third-party secrets stay server-side.** BarentsWatch and ADS-B provider
  credentials must never reach the browser; the BFF is the only place that
  holds them.
- Adds one more service to run and deploy (see phase 2 and phase 10), and one
  more hop of latency between the browser and the data it displays.
